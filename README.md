# Multi-Agent Data Processor

Multi-Agent System (MAS) for industrial IoT telemetry refinement and analytics.

The project processes telemetry generated by an industrial machine composed of 36 heads. Each head provides:

- cumulative closure count;
- applied torque measurement;
- machine status.

The system ingests telemetry files, validates and refines the data, detects closure events, computes production KPIs, performs deterministic analytics and generates a structured industrial report.

---

## Project Goal

The goal of the project is to build a Multi-Agent System able to:

- ingest industrial telemetry data;
- validate schema, timestamps, missing values and unit metadata;
- detect closure events from cumulative counters;
- refine low-quality events;
- identify counter resets and discontinuities;
- calculate production speed;
- analyse torque behaviour over time;
- detect torque anomalies and drift;
- analyse correlations between machine heads;
- detect machine idle periods;
- generate a structured final report.

---

## Multi-Agent Architecture

The application is organised as a coordinated Multi-Agent System.

### Ingestion Agent

Responsible for:

- reading input files;
- supporting CSV, JSON and Parquet formats;
- validating required columns;
- validating timestamps;
- detecting missing values;
- validating measurement unit metadata.

### Data Quality Agent

Responsible for:

- detecting counter increments;
- identifying closure events;
- classifying machine status;
- detecting counter drops;
- identifying counter recovery events;
- detecting temporal data gaps;
- removing invalid counter recovery events;
- maintaining continuity between consecutive files.

### Analytics Agent

Responsible for:

- counting total closure cycles;
- counting production pieces;
- calculating cycle speed;
- calculating production speed;
- updating production speed using an incremental average;
- computing torque statistics;
- computing daily torque trends;
- computing moving averages;
- detecting torque drift;
- detecting statistical torque anomalies;
- calculating correlations between heads;
- calculating residual correlations;
- detecting idle periods.

### Report Agent

Responsible for producing a structured report containing:

1. goal;
2. analysed data;
3. performed analyses;
4. findings;
5. confidence and limitations;
6. suggested next checks.

### Multi-Agent Coordinator

The `MultiAgentCoordinator` manages the execution order of the agents and transfers the processing context between them.

The processing flow is:

```text
Input ZIP
   |
   v
Ingestion Agent
   |
   v
Data Quality Agent
   |
   v
Analytics Agent
   |
   v
Report Agent
   |
   v
Final Industrial Report
```

## Input Data

The system expects ZIP archives containing supported telemetry files.

Supported formats:

- `.csv`
- `.json`
- `.parquet`

The default input directory is:

```text
data/raw
```

Each telemetry dataset is expected to contain:

```text
timestamp

H01 Count
H01 AppTorque
H01 Status

...

H36 Count
H36 AppTorque
H36 Status
```

The number of machine heads (e.g., `H01` to `H48`) is extracted dynamically from the telemetry dataset, conforming to a Configuration-Driven architecture without any hard-coded limits.

## Event Detection

Closure events are detected by comparing the cumulative counter of each head with its previous value.

For each head:

```text
Count Difference = Current Count - Previous Count
```

A positive difference represents one or more closure cycles.

The detected event contains:

- timestamp;
- head;
- current count;
- previous count;
- count difference;
- AppTorque;
- machine status.

The system preserves the previous counter and timestamp between consecutive input files.

---

## Status Classification

The currently known status codes are:

| Status | Classification |
|--------|----------------|
| 0 | Closure OK |
| 2 | No Load |
| 3 | Failing to reach first torque threshold |
| 4 | No Closure |
| 5 | Failing to reach final torque |
| 8 | No InTorque |
| 9 | Closure Head raises before TimeInTorque |
| 16 | No CapTurns |
| 17 | Cap closed with less degrees than CapTurns |
| 32 | Following Error |
| 33 | Tracking error between real and controlled position |
| 64 | Bad Closure |
| 65 | ClosureTorque reached but cap still rotating |
| other | Unknown |

Unknown status codes are intentionally preserved instead of assigning an undocumented meaning.

## Data Quality

Detected events are classified into the following data-quality categories:

### Valid

The event is considered valid.

### Counter Recovery

A large positive counter increment occurring after a previous counter value of zero.

These events are excluded from the cleaned event set because they may represent counter reinitialisation rather than real production.

### Data Gap

An event occurring after an unusually large timestamp gap.

Data Gap events are retained but explicitly marked.

### Counter Drops

Negative counter differences are analysed separately.

The system records:

- total counter drops;
- drops to zero;
- drops to non-zero values;
- number of unique drop timestamps.

Counter drops to zero may be consistent with counter resets or reinitialisation, but the software does not assume a specific machine cause.

## Production KPIs

Two production speed metrics are calculated.

### Cycle Speed

Based on the total number of counter increments.

```text
cycle speed =
total closure cycles / elapsed time
```

The result is expressed in pieces per hour.

### Production Speed

Production pieces include:

- Closure OK;
- Bad Closure.

No Load events are excluded from production.

```text
production speed =
production pieces / elapsed time
```

The system updates production speed incrementally while processing consecutive files.

---

## Torque Analysis

Torque analytics are performed independently for every machine head.

Calculated statistics include:

- number of events;
- average;
- standard deviation;
- minimum;
- maximum;
- number of zero values.

The physical unit of `AppTorque` is not specified in the available dataset.

For this reason, the project does not assume or invent a physical unit.

---

## Daily Torque Trend

The system calculates daily torque averages for each head.

A configurable moving average is also calculated to highlight longer-term behaviour.

Default configuration:

```text
MOVING_AVERAGE_WINDOW_DAYS = 7
```

---

## Torque Drift Detection

Torque drift is detected by comparing the current daily average with a baseline calculated from previous days.

The main configuration parameters are:

```text
DRIFT_WINDOW_DAYS = 7
DRIFT_THRESHOLD = 0.1
DRIFT_MIN_EVENTS = 500
```

The detected direction can be:

```text
Increase
Decrease
```

Drift detection is a deterministic analytical heuristic and should be interpreted together with machine context.

---

## Torque Anomaly Detection

Torque anomalies are detected statistically using the interquartile range.

Configuration:

```text
ANOMALY_IQR_MULTIPLIER = 3.0
ANOMALY_MINIMUM_MARGIN = 0.05
ANOMALY_MIN_EVENTS = 100
```

Detected anomalies are statistical outliers.

They do not automatically represent machine failures.

---

## Head Correlation Analysis

The system calculates correlations between machine heads using their daily torque behaviour.

Two types of correlation are produced.

### Raw Correlation

Correlation calculated directly from daily head averages.

### Residual Correlation

The machine-wide daily average is removed before calculating correlation.

Residual correlations help reduce common machine-level trends and highlight relationships that may be more specific to individual heads.

Correlation does not imply causation.

---

## Idle Period Detection

The system identifies periods where all 36 machine heads simultaneously have:

```text
Status = 2
```

which corresponds to:

```text
No Load
```

A period is considered idle when the condition is sustained for at least:

```text
IDLE_MIN_DURATION_SECONDS = 60
```

The algorithm also verifies continuity between timestamps.

```text
IDLE_MAX_GAP_SECONDS = 2
```

An idle period means all heads were in No Load state. It does not necessarily mean that the machine was powered off.

## Running the Pipeline

The default command is:

```bash
py main.py
```

The system automatically searches for ZIP files inside:

```text
data/raw
```

A different input folder can be specified using the CLI:

```bash
py main.py --input path/to/input
```

Example:

```bash
py main.py --input smoke_input
```

CLI help:

```bash
py main.py --help
```

The program reports an error when:

- the input directory does not exist;
- no ZIP archives are available in the selected directory.

## Interactive Agentic CLI (bot.py)

After successfully running the pipeline (`py main.py`), the system saves the analytical context in `data/processed/context.pkl`. 
You can then query the machine data using natural language through the interactive Agentic AI bot.

To start the bot, you must provide your Google Gemini API key as an environment variable. If you don't have one, you can get a free API key from [Google AI Studio](https://aistudio.google.com/app/apikey):

```bash
export GOOGLE_API_KEY="your_api_key_here"
py bot.py
```

The bot uses a ReAct (Reason and Act) loop to autonomously call Python tools, process mathematical queries, and generate on-demand reports and Matplotlib charts without hallucinating data.

## Report Limitations

The generated report explicitly states important interpretation limits.

In particular:

- torque anomalies are statistical outliers and do not directly indicate machine failures;
- correlations between heads do not imply causation;
- production speed represents an average over the observed interval;
- the physical measurement unit of `AppTorque` is not available in the provided dataset.
